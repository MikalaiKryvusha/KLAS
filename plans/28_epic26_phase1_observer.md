> **Вовне:** журнал этой фазы — доказательная база для ответов владельца в `interviews/013`

## Вектор цели фазы

Правило «видеокарта занята» нельзя вывести из головы. Мы не знаем, как выглядит **на числах**
разница между «владелец играет», «идёт рендер в DaVinci», «смотрит кино с SVP», «открыл браузер с
аппаратным декодированием» и «отошёл от компьютера». Пока не знаем — сторож будет либо выгонять
модель от каждого чиха, либо проспит настоящую нагрузку.

Фаза строит **датчик, который ничего не делает**: смотрит, записывает, молчит. Её продукт — не код
сторожа, а **сутки настоящей жизни машины в журнале**, по которым правила можно проверить задним
числом, не трогая ни модель, ни владельца.

Якорь мета-плана: *«Датчик, который ошибается, но ничего не делает, стоит ноль; исполнитель, который
ошибается, отнимает у владельца карту»*.

## Критерии приёмки фазы

| # | Критерий | Как проверяется | Порог |
|---|---|---|---|
| **Ф1-1** | Журнал покрывает ≥ 24 часа непрерывной реальной жизни машины | метки времени в журнале, разрывов нет | ≥ 24 ч |
| **Ф1-2** | В журнале есть минимум по одному эпизоду каждого класса: игра · рендер/тяжёлый GPU · видео · простой · работа владельца без GPU | разметка эпизодов владельцем или по именам процессов | 5 классов |
| **Ф1-3** | Правило-кандидат, прогнанное ПО ЖУРНАЛУ, верно опознаёт каждый эпизод | офлайн-прогон правила на записи | 0 ложных срабатываний |
| **Ф1-4** | Наблюдатель не изнашивает диск | размер журнала за сутки | ≤ 1 МБ (П7 эпика) |
| **Ф1-5** | Наблюдатель видит простой ВЛАДЕЛЬЦА, а не свой | сверка: отойти на 10 минут, найти это в журнале | эпизод найден |

## Ключевые решения конструкции — приняты разведкой, не на ходу

1. **Живёт в сессии пользователя, не службой.** `GetLastInputInfo` возвращает простой ТОЛЬКО той
   сессии, которая его вызвала; служба Windows живёт в сессии 0 и увидит собственный простой, а не
   владельца (`researches/29`, ловушка). ⚠️ Это расходится с интервью 010 («Q1 = A, служба Windows»)
   — расхождение осознанное и относится только к сторожу.
2. **Пишем СЫРЫЕ факты, а не вердикты.** В журнал идут числа (сколько памяти занято, кем, какая
   утилизация, сколько секунд простоя), а не «занято/свободно». Тогда пороги можно перебирать
   офлайн по одной и той же записи, не собирая данные заново. Иначе каждая правка порога — новые
   сутки ожидания.
3. **Запись только на СМЕНУ состояния** (правило Р1 эпика): опрос раз в 2–3 секунды, строка в журнал
   — когда что-то изменилось существенно, плюс контрольная строка раз в 5 минут. Наивная строка на
   каждый тик — это ~30 000 мелких записей в сутки, и ровно этого владелец просил не делать.
4. **Ни одного действия.** Наблюдатель не вызывает `unload`, не трогает `ttl`, не поднимает модель.
   Ноль риска — единственная причина, по которой его можно запускать, не дожидаясь ответов владельца.
5. **Инструмент — PowerShell**, потому что ему одному доступны и `GetLastInputInfo` (через
   `Add-Type` P/Invoke), и `nvidia-smi`, без сторонних зависимостей. ⚠️ Файл пишется **чисто ASCII**
   (EXP-0066); проверка — `npm run guard:ps1`.

## Шаги

### Ш1. Наблюдатель `tools/gpu-watch.ps1`
Якорь: *«опрос NVML… + `GetLastInputInfo` + список процессов. Пишет ЖУРНАЛ и больше ничего»*.

- [ ] Опрос раз в 3 с: `nvidia-smi` — занято/свободно МиБ, утилизация, список процессов на карте с
      именами и их память.
- [ ] Простой владельца — `GetLastInputInfo` через `Add-Type`.
- [ ] Имя процесса активного окна (переднего плана) — как дополнительный признак.
- [ ] Загружена ли НАША модель — `GET http://127.0.0.1:8080/running`.
- [ ] Строка журнала — одна JSON-строка на событие в `logs/gpu-watch/<дата>.jsonl`.
- [ ] Запись только на смену состояния + контрольная строка раз в 5 минут (правило Р1).
- [ ] Ключи ASCII, файл ASCII.

**Проверка наблюдением:** `npm run guard:ps1` зелёный; 10 минут работы дают связный журнал, где
видно запуск и закрытие любого GPU-приложения.

### Ш2. Самопроверка датчика
- [ ] Ключ `--selftest`: один опрос, печать всех снятых величин, код возврата 0.
- [ ] Ручная сверка: цифры совпадают с `nvidia-smi` и с реально запущенными программами.

**Проверка:** вывод самопроверки приложен к плану как свидетельство.

### Ш3. Запуск в сессии пользователя и переживание перезагрузки
- [ ] Задача планировщика с триггером «вход в систему», **в контексте пользователя** (не SYSTEM).
- [ ] Смоук: перезагрузить машину, убедиться, что журнал продолжился.
- [ ] Выключатель: как остановить одной командой — записать в шапку скрипта.

**Проверка:** после перезагрузки в журнале есть строки; `Ф1-5` подтверждён отлучкой на 10 минут.

### Ш4. Собрать сутки и разметить эпизоды
- [ ] ≥ 24 часа непрерывной записи обычной жизни машины.
- [ ] Отметить, что происходило: игра, рендер, кино, простой, работа без GPU (Ф1-2). Разметку можно
      снять по именам процессов, спорные места — вопросом владельцу одной строкой.

**Проверка:** Ф1-1 и Ф1-2 выполнены; размер журнала укладывается в Ф1-4.

### Ш5. Прогнать правила-кандидаты ПО ЖУРНАЛУ
Якорь мета-плана: *«правило верно опознало каждый эпизод при нуле ложных срабатываний»*.

- [ ] `tools/gpu-watch-replay.mjs`: читает журнал, применяет правило с заданными порогами, печатает
      таблицу «эпизод → вердикт правила → верно/ложно».
- [ ] Прогнать три варианта из `interviews/013` Q1: любой чужой процесс · порог по памяти и
      утилизации · только полный экран.
- [ ] Выбрать пороги, при которых ложных срабатываний ноль.

**Проверка:** таблица сравнения трёх правил на ОДНОМ журнале — это и есть материал, с которым идти
к владельцу в `interviews/013`, вместо предложенных наугад чисел.

### Ш6. Вернуть вывод в эпик
- [ ] Дописать в `plans/26` найденные пороги и то, какое правило выжило.
- [ ] Если журнал показал класс нагрузки, которого мы не предвидели, — записать его отдельно.

## Риски фазы

| Риск | Чем гасим |
|---|---|
| Наблюдатель в сессии 0 слеп к простою владельца | Ш3 ставит задачу в контексте пользователя; Ф1-5 это проверяет отлучкой |
| Журнал распухнет и начнёт изнашивать диск | правило Р1 (запись на смену состояния); Ф1-4 меряет |
| Опрос раз в 3 с нагрузит машину | `nvidia-smi` дёшев; замерить долю CPU и записать числом |
| Сутки записи не поймают редкий сценарий (например, рендер) | Ф1-2 требует все пять классов; не хватило — продлить наблюдение, а не додумать |
| Скрипт с кириллицей развалит парсер PowerShell | файл чисто ASCII; ворота `npm run guard:ps1` (EXP-0066) |

## Что фаза НЕ делает

Не выгружает и не загружает модель, не меняет `ttl`, не принимает решений. Её продукт — журнал и
проверенное на нём правило. Действовать начинает фаза 2, и её операционный план пишется, когда эта
фаза закроется.
