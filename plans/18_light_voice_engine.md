У владельца **уже выбран голос** — `voice/out/candidates/JARVIS/espeech_bystree.mp3` (движок

## Три трека — заказаны владельцем все три

### ⛔ Трек А. ЗАКРЫТ ЗАМЕРОМ 2026-07-30 — процессор этот класс движков не тянет

**Гипотеза была:** если уже одобренный движок идёт на процессоре быстрее реального времени,
задача исчезает целиком — владелец получает ровно тот голос, который выбрал, и VRAM не нужна
вовсе. Все прежние RTF (0.167–0.197) сняты на GPU; на CPU не мерил никто.

**Замер (`tools/voice/tts-cpu-bench.py`, ESpeech RL-V2, Ryzen 5700G, 8 потоков torch, GPU скрыта,
фраза 66 символов → 4.30 с звука):**

| `nfe_step` | синтез | RTF | вердикт |
|---|---|---|---|
| 32 (умолчание) | **212.6 с** | **49.4** | медленнее реального времени в 49 раз |
| 16 | 98.0 с | 22.8 | — |
| 8 (уже с потерей качества) | 49.2 с | **11.4** | даже вчетверо урезанный решатель не спасает |

Холодный старт 8.8 с · пик RAM 5 035 МБ · VRAM 0.

**Вывод:** фраза на 4 секунды синтезируется 3.5 минуты. Не годится ни для живого разговора, ни
даже для подготовленной речи. **CPU-путь для flow-matching движков закрыт.** Замерять F5 для JOI
отдельно смысла нет — та же архитектура, те же 330 М параметров, тот же решатель.

⚠️ Мерить такое можно только на СВОБОДНОМ процессоре: рядом с обучением (6 воркеров загрузки
данных) стенд измерил бы конкуренцию за CPU, а не движок (класс EXP-0033). Обучение на время
замера останавливалось.

#### ⚠️ Открытый вопрос ВЛАДЕЛЬЦУ: сколько транслитерации нужно мультиязычному движку

Наш слой `text_norm` в режиме `abbrev` всё равно транслитерирует имена — правило писалось под
ОДНОязычные движки. Для мультиязычного это возвращает ровно тот костыль, ради снятия которого
кандидат и взят, и даёт гибриды:

| в тексте | `abbrev` (канон) | `off` |
|---|---|---|
| `llama.cpp` | «лама си-плюс-плюс» | `llama.cpp` |
| `Open WebUI` | «**Open** веб-ю-ай» ← полулатиница | `Open WebUI` |
| `RTX 5070 Ti` | «Эр-Ти-Икс … Ти-Ай» | `RTX … Ti` |
| `npm run build` | «эн-пи-эм run build» | `npm run build` |

Числа в слова превращаются в ОБОИХ режимах — регрессии `bugs/13` нет ни в одном (проверено).
**Решение — за владельцем, судить на слух не работа агента (EXP-0031)** ⇒ выдать ОБА варианта.

## 🧭 Куда сузилось поле после закрытия трека А

CPU отпал, а Piper (маленькая модель) отвергнут владельцем по звуку. Значит остаются ровно два
направления, и второе — решение владельца, а не агента:

1. **Квантованная сборка хорошего движка, влезающая в свободные ~950 МБ.** Тут появляется цифра,
   которой раньше не было на столе: **CosyVoice 3 это 0.5B, и в Q4 его llm-часть весит ~0.4 ГБ**
   (`Lourdle/Fun-CosyVoice3-0.5B-2512-GGUF` несёт всю лестницу квантов). Это единственный
   кандидат, который по РАЗМЕРУ помещается рядом с загруженной LLM. Он же мультиязычный, то есть
   заодно снимает костыль транслитерации. Цена — свой рантайм (см. поправку в треке В).
2. **Освободить VRAM под движок** — то есть взять модель поменьше на время голосового сеанса.
   ⛔ Урезание контекста уже проверено и НЕ работает: с 98K до 32K освободилось всего 330 МБ,
   память ест не KV-кеш, а веса. Значит это выбор «меньше ум ради голоса», и делает его владелец.

## Определение готовности плана

Владелец слышит голос **выбранного им класса качества** в живом разговоре, и этот голос не
отбирает у основной модели столько VRAM, чтобы она перестала помещаться. Мерится: вердикт
владельца по звуку + `nvidia-smi` при работающей LLM + RTF на реальной фразе.
