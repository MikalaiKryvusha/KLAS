# Bug 15 — Гейтвей OpenClaw умирает сам, молча и без следа

**Статус:** 🔬 ИССЛЕДОВАНИЕ (корень НЕ установлен; наблюдаемость починена)
**Версия/сборка:** OpenClaw 2026.7.1 · node 24.15.0 · движок llama.cpp b10167
**Когда/контекст:** замечен 2026-07-29 утром; документ заведён 2026-07-29 в 13:5x

## Симптом

Гейтвей найден упавшим: `llama-swap` жив, LLM отвечает 200, а порт **18789 молчит и процесса нет**.
Никто его не гасил. Поднят канонически (`node openclaw.mjs gateway run`) — работает дальше как ни в
чём не бывало. Причина не установлена: **процесс исчез между прогонами**.

**Почему это дороже, чем выглядит:** с 2026-07-28 гейтвей — не опция, а рабочий путь к ядру
(`POST /v1/chat/completions` на резидентное ядро, −8.4…10.6 с на ход). **Голосовой тракт без
гейтвея не работает вовсе**, а приоритет №1 владельца — стабильность.

## Воспроизведение

❌ **Детерминированного воспроизведения НЕТ** — событие наблюдалось один раз. По
`BUG_FIXING_FRAMEWORK.md` это делает баг задачей на *исследование*, а не на слепой фикс.

## Криминалистика

### Находка №1 — почему улик не было: мы сами их выбрасывали

`tools/klas.ps1` поднимал гейтвей так:

```powershell
Start-Process node -ArgumentList "$OpenclawJs",'gateway','run' -WindowStyle Hidden
```

Без `-RedirectStandard*`. Скрытое окно закрывается вместе с процессом ⇒ **предсмертный вывод
(stack trace, OOM, сообщение об ошибке) уходил в никуда.** В `~/.openclaw/logs/` лежит только
`config-audit.jsonl` — ни строки о работе гейтвея.

**Починено (см. «Фикс наблюдаемости»).**

### Находка №2 — собственный лог OpenClaw существует, просто не там, где его искали

Перехваченный stdout сразу назвал адрес:

```
[gateway] log file: C:\Users\krinik\AppData\Local\Temp\openclaw\openclaw-2026-07-29.log
```

То есть **улика жила на диске всё это время** — в `%TEMP%\openclaw\`, а не в `~/.openclaw/logs\`.
Это ровно урок EXP-0019 (ищи артефакт, который система уже сохранила), применённый не с той стороны:
я искал в доме приложения, а лог во временной папке.

Наличные файлы на 2026-07-29: `openclaw-2026-07-28.log` (715 КБ), `openclaw-2026-07-29.log` (574 КБ,
480 строк), `gateway.<hash>.lock`.

**Формат — JSONL со структурой `{"0":"{\"subsystem\":\"…\"}","1":<сообщение>,"_meta":{…}}`**, а не
текстовые строки, поэтому наивный `Select-String 'fatal|error'` по нему **не находит ничего** — что и
произошло при первом заходе. Разбирать его нужно как JSON, по полю `subsystem`.

⚠️ **Читать оба лога только с `-Encoding UTF8`:** файлы UTF-8, а PowerShell 5.1 по умолчанию читает
их как ANSI и показывает моджибейк (`configurationвЂ¦`) — тот же класс, что `bugs/08`, только на
стороне чтения. Это не дефект гейтвея.

### Что проверено и НЕ дало ответа

- Поиск `fatal|uncaught|unhandled|ERROR|exiting|SIGTERM|out of memory` по логу дня — **ноль
  совпадений** (но см. оговорку про формат выше: поиск шёл по неверной модели файла, его надо
  повторить разбором JSON).
- Маркеры `[gateway] starting…` / `[gateway] ready` в `%TEMP%`-логе отсутствуют — они идут в stdout,
  который до сегодняшнего дня не сохранялся. Значит **границы жизней процесса** по старым логам
  восстановить нельзя, а начиная с сегодня — можно.

## Гипотезы (ранжированы, ни одна не проверена)

1. **Процесс убит извне вместе с родителем.** Гейтвей стартовал как дочерний от сессии агента/
   терминала; закрытие родителя (или `Stop-Process` по маске `node.exe` в чужом скрипте) уносит его.
   Самая «лошадиная» гипотеза: `klas.ps1 down` гасит node **по строке команды**, но любой другой
   массовый `Stop-Process node` — нет.
2. **Необработанное исключение в канале/сайдкаре.** `starting channels and sidecars…` — падение
   плагина могло уронить процесс без записи в JSONL-лог (вывод шёл в потерянный stdout).
3. **Нехватка памяти.** 32 ГБ RAM делятся с LLM-стеком и docker; OOM-kill node не логирует сам.
4. **Плановый выход по health-monitor.** В логе виден `[health-monitor] started (interval: 300s…)` —
   надо прочитать, есть ли у него право завершать процесс.

## Фикс наблюдаемости (сделан) — но НЕ фикс дефекта

`tools/klas.ps1`: вывод гейтвея перехватывается в `F:\KLAS\logs\gateway-<ГГГГММДД-ЧЧММСС>.out.log`
и `.err.log`. Метка времени в имени обязательна: перенаправление `Start-Process` открывает файл **на
перезапись**, и без метки перезапуск затирал бы предсмертный вывод — то есть «фикс» уничтожал бы
ровно ту улику, ради которой делается.

`.gitignore` уже покрывает (`logs/`, `*.log`) — новых правил не потребовалось.

**Проверено наблюдением 2026-07-29** (гейтвей убит и поднят штатным `klas.ps1 -Action up`):

| Проверка | Результат |

причина, а не наличие логов.

## Следующие шаги

1. Разобрать `%TEMP%\openclaw\openclaw-2026-07-2*.log` **как JSONL** (по `subsystem`), а не грепом:
   найти последние события перед провалом и проверить гипотезу 2 и 4.
2. Прочитать в исходниках OpenClaw, при каких условиях `health-monitor` завершает процесс.
3. Если падение повторится — первым делом `F:\KLAS\logs\gateway-*.err.log` за нужную метку времени.
4. Рассмотреть постоянный сервис (`openclaw gateway install`, домашка из интервью 005): служба
   переживает закрытие родителя и лечит гипотезу 1 механически.

## Решения, принятые без владельца

- **Логи кладу в `F:\KLAS\logs\`, а не в `%TEMP%`.** Временная папка чистится Windows — улика может
  исчезнуть до того, как её прочтут. Проект уже игнорирует `logs/`, новых сущностей ноль.
- **Файл на каждый запуск вместо одного растущего.** Дороже по числу файлов, но не теряет
  предсмертный вывод при перезапуске; ротацию не пишу, пока не понадобится (Оккам).
- **Гейтвей перезапущен в ходе проверки** (он был поднят и работал). Правку нельзя было объявить
  рабочей, не прогнав её на живом процессе; простой — секунды, владельца за компом нет.
