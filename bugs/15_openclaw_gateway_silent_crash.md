# Bug 15 — Гейтвей OpenClaw умирает сам, молча и без следа

**Статус:** 🔬 ИССЛЕДОВАНИЕ (корень НЕ установлен; наблюдаемость починена)
**Версия/сборка:** OpenClaw 2026.7.1 · node 24.15.0 · движок llama.cpp b10167
**Когда/контекст:** замечен 2026-07-29 утром; документ заведён 2026-07-29 в 13:5x

## Симптом

Гейтвей найден упавшим: `llama-swap` жив, LLM отвечает 200, а порт **18789 молчит и процесса нет**.
Никто его не гасил. Поднят канонически (`node openclaw.mjs gateway run`) — работает дальше как ни в
чём не бывало. Причина не установлена: **процесс исчез между прогонами**.

**Почему это дороже, чем выглядит:** с 2026-07-28 гейтвей — не опция, а рабочий путь к ядру
(`POST /v1/chat/completions` на резидентное ядро, −8.4…10.6 с на ход). **Голосовой тракт без
гейтвея не работает вовсе**, а приоритет №1 владельца — стабильность.

## Воспроизведение

❌ **Детерминированного воспроизведения НЕТ** — событие наблюдалось один раз. По
`BUG_FIXING_FRAMEWORK.md` это делает баг задачей на *исследование*, а не на слепой фикс.

## Криминалистика

### Находка №1 — почему улик не было: мы сами их выбрасывали

`tools/klas.ps1` поднимал гейтвей так:

```powershell
Start-Process node -ArgumentList "$OpenclawJs",'gateway','run' -WindowStyle Hidden
```

Без `-RedirectStandard*`. Скрытое окно закрывается вместе с процессом ⇒ **предсмертный вывод
(stack trace, OOM, сообщение об ошибке) уходил в никуда.** В `~/.openclaw/logs/` лежит только
`config-audit.jsonl` — ни строки о работе гейтвея.

**Починено (см. «Фикс наблюдаемости»).**

### Находка №2 — собственный лог OpenClaw существует, просто не там, где его искали

Перехваченный stdout сразу назвал адрес:

```
[gateway] log file: C:\Users\krinik\AppData\Local\Temp\openclaw\openclaw-2026-07-29.log
```

То есть **улика жила на диске всё это время** — в `%TEMP%\openclaw\`, а не в `~/.openclaw/logs\`.
Это ровно урок EXP-0019 (ищи артефакт, который система уже сохранила), применённый не с той стороны:
я искал в доме приложения, а лог во временной папке.

Наличные файлы на 2026-07-29: `openclaw-2026-07-28.log` (715 КБ), `openclaw-2026-07-29.log` (574 КБ,
480 строк), `gateway.<hash>.lock`.

**Формат — JSONL со структурой `{"0":"{\"subsystem\":\"…\"}","1":<сообщение>,"_meta":{…}}`**, а не
текстовые строки, поэтому наивный `Select-String 'fatal|error'` по нему **не находит ничего** — что и
произошло при первом заходе. Разбирать его нужно как JSON, по полю `subsystem`.

⚠️ **Читать оба лога только с `-Encoding UTF8`:** файлы UTF-8, а PowerShell 5.1 по умолчанию читает
их как ANSI и показывает моджибейк (`configurationвЂ¦`) — тот же класс, что `bugs/08`, только на
стороне чтения. Это не дефект гейтвея.

### Находка №3 — разбор JSONL: улики ЕСТЬ, грепом их не видно

Первый заход искал `fatal|uncaught|ERROR` построчным грепом и дал **ноль** — потому что искал не в
той модели файла. Разбор 395 записей как JSON (`_meta.date`, `_meta.logLevelName`, `subsystem`) сразу
дал три записи уровня **WARN** за день:

| Время (локальное) | Подсистема | Сообщение |
|---|---|---|
| 09:55:36 | `agent/embedded` | `empty response detected: runId=chatcmpl_092a0bf2… ` |
| **09:57:13** | **`diagnostic`** | **`liveness warning: reasons=event_loop_delay interval=31s eventLoopDelayP99Ms=1036.5 eventLoopDelayMaxMs=1152.4`** |
| 10:25:19 | `agent/embedded` | `[trace:embedded-run] prep stages: runId=chatcmpl_e0e6dde1…` |

**Главная из них — вторая.** У гейтвея есть собственная подсистема `diagnostic`, и она за полтора
часа до обнаружения трупа сообщила, что **событийный цикл node вставал более чем на секунду**
(P99 1036 мс, max 1152 мс). Это ровно тот класс симптома, который предшествует зависанию/падению
однопоточного процесса, и это первое объективное свидетельство, что гейтвею в то утро было плохо.

Отдельно стоит заметить `empty response detected` в 09:55 — это, вероятно, та же сущность, что
строки-заглушки ядра из `bugs/12` («No response from OpenClaw.»), только со стороны гейтвея.

### Находка №4 — контрольная проверка: `liveness warning` НЕ фоновый шум

Находка №3 сама по себе ничего не значила бы, будь такие предупреждения обычным делом
(`BUG_FIXING_FRAMEWORK.md`: «находка — не находка, пока не проверена»). Прогнан тот же разбор по
логу **предыдущего дня** — `openclaw-2026-07-28.log`, 530 записей:

| | 2026-07-28 (гейтвей выжил) | 2026-07-29 (гейтвей умер) |
|---|---|---|
| записей всего | 530 | 395 |
| НЕ-INFO записей | **91** | 3 |
| **`liveness warning`** | **0** | **1** |

Причём 28-е было днём ЗАМЕТНО тяжелее: 34 `lane task error`, десятки `model_fallback_decision` и
`embedded_run_failover_decision`, `LLM r…`-ошибки, `config change requires gateway restart` — то есть
гейтвей работал в стрессе и всё равно НИ РАЗУ не пожаловался на событийный цикл.

**Вывод: единственное за два дня предупреждение о блокировке цикла выпало ровно на тот день, когда
процесс умер.** Это не доказательство причины (совпадение возможно, выборка — два дня), но это
переводит гипотезу 0 из догадки в **приоритетную версию**, а заодно даёт готовый охранник: если
`diagnostic/liveness warning` появится снова — смотреть на гейтвей немедленно.

будет определено с точностью до секунды.

## 🔁 ВОСПРОИЗВЕДЕНИЕ 2026-07-29 14:45:56 — и утренняя правка окупилась

Гейтвей умер **второй раз за день**, прямо посреди прогона `voice-bench`. На этот раз он оставил
улику — ровно ради этого утром и делался перехват вывода.

**Что видно в нашем `logs\gateway-20260729-133423.out.log` (последние строки):**

14:45:50  [tool-policy] removed 3 tool(s) …                              ← начался 5-й

Все предыдущие ходы дают устойчивый рисунок `start → response status=200 → текст → stopReason=stop`.

### Что это исключает (проверено, а не предположено)

| Проверка | Результат | Что отсекает |
|---|---|---|
| порт 18789 / процессы | молчит, 0 процессов | гейтвей действительно умер, а не завис |
| `llama-server` / порт 8080 | **жив**, 8.2 ГБ RSS, слушает | умер НЕ весь стек, а только гейтвей |
| журнал ОС «Приложение» за час | **пусто** | Windows падения не регистрировала ⇒ не аварийное завершение |
| свободная память | **8.7 ГБ из 32 ГБ** | нехватка памяти машины отпадает |
| `stderr` гейтвея | последняя запись за минуту ДО смерти | предсмертного исключения нет вовсе |
| `liveness warning` в JSONL | **в этот раз НЕТ** | ⚠️ утренняя гипотеза 0 как ПРЕДВЕСТНИК не подтвердилась |

**Портрет отказа:** процесс Node завершается **тихо и чисто** — без исключения, без записи ОС, без
предсмертного вывода, при живой машине и живом LLM. Так не умирают от ошибки; так выходят по команде
или по внутреннему решению кода.

### ⭐ Новая корреляция, самая ценная за день

**Оба падения произошли во время прогона `voice-bench`.** Бенч создаёт **НОВУЮ сессию на каждый
кейс** (`user: bench-<метка времени>`), а трасса подготовки в логе показывает, что каждая новая
сессия стоит дорого:

```
prep stages: … bundle-tools:6846ms@7359ms, system-prompt:1547ms@8906ms, stream-setup:1230ms@10147ms
```

То есть **10 секунд подготовки и ~7 с только на сборку инструментов — на КАЖДУЮ новую сессию**.
Отсюда рабочая гипотеза: гейтвей не переживает **быструю смену сессий**, а не «просто работу».
Это объясняет и то, почему владелец видит падения редко (у него один длинный диалог), и почему их
дважды поймал агент (бенч гоняет 7 сессий подряд).

⚠️ **Чего я НЕ могу исключить честно:** что процесс убил кто-то из моих же инструментов. `klas.ps1
down` ищет процесс по строке команды и в это время не запускался, широкого `Stop-Process node` в
сессии не было — но полного доказательства «его никто не убивал» у меня нет, а отсутствие улики
уликой не является.

## 🧪 Попытка воспроизвести по требованию (2026-07-29, после второго падения) — НЕ УДАЛОСЬ

Построен минимальный стенд **`node tools/gateway-churn-probe.mjs [N] [--same]`**: гоняет N ходов,
создавая НОВУЮ сессию на каждый, без рта, ушей, файлов и воспроизведения. Смысл разделения: если
падает здесь — виноват гейтвей, и весь голосовой тракт оправдан; если не падает — подозрение
возвращается к тракту.

| Эксперимент | Результат |
|---|---|
| 12 ходов, НОВАЯ сессия на каждый | ✅ гейтвей пережил все 12 (7.5–9.7 с на ход, все `stop`) |
| полный `voice-bench` (7 кейсов, рот + уши + воспроизведение) | ✅ пережил, **34/35** |

**Вывод: гипотеза «не переживает быструю смену сессий» ОПРОВЕРГНУТА этим прогоном**, а сам дефект
**по требованию не воспроизводится**. Оба пути, на которых он проявлялся, отработали чисто.

Значит это **перемежающийся отказ**, и по `BUG_FIXING_FRAMEWORK.md` он остаётся задачей на
исследование, а не на фикс: патчить наугад тут нечего. Практический вывод другой и он важнее —
**ловушка уже стоит**: перехват вывода включён, и следующее падение снова оставит улику. Накопление
двух-трёх таких улик даст рисунок, которого не даст ни одна догадка.

⚠️ Что НЕ надо делать следующей сессии: «починить» это перезапуском по таймеру или вотчдогом.
Автоперезапуск замаскирует симптом и уничтожит единственный способ найти причину — а голосовой тракт
без гейтвея не работает вовсе, то есть цена ошибки здесь высокая.

**Осталось непроверенным (следующий кандидат):** оба падения случились при высокой загрузке CPU
(рот и уши считают на тех же ядрах, что и гейтвей), а утром зафиксирована стойка событийного цикла.
Стенд `gateway-churn-probe` CPU почти не грузит — этим он и отличается от бенча. Проверять так:
гонять churn-стенд ОДНОВРЕМЕННО с нагрузкой на все ядра.

## Гипотезы (ранжированы; после разбора JSONL порядок изменился)

0-bis. **⭐⭐ ГЛАВНАЯ после воспроизведения: гейтвей не переживает БЫСТРУЮ СМЕНУ СЕССИЙ.** Оба падения
   пришлись на прогон `voice-bench`, который создаёт новую сессию на каждый кейс ценой ~10 с
   подготовки (`bundle-tools` 6.8 с). Проверять так: погонять N новых сессий подряд БЕЗ звука и
   ушей — минимальный воспроизводитель, если он падает, дефект локализован; если нет, гипотеза
   отпадает и остаётся смотреть на смежные подсистемы. Это самый дешёвый следующий эксперимент.

0. **~~Самая обеспеченная уликой:~~ процесс вставал ещё до смерти — ОСЛАБЛЕНА воспроизведением.**
   При падении 14:45 никакого `liveness warning` не было вовсе, то есть как ПРЕДВЕСТНИК стойка цикла
   не подтвердилась. Утреннее совпадение остаётся любопытным, но одиночным. В 09:57 его собственная
   подсистема `diagnostic` зафиксировала блокировку событийного цикла на 1.0–1.15 с. Если цикл
   блокируется на секунды, гейтвей перестаёт отвечать на порт, и «процесса нет» могло быть
   следствием чужого таймаута/убийства зависшего процесса, а не самопроизвольного выхода. Что
   проверять: связаны ли `empty response` (09:55) и стойка цикла (09:57) с тяжёлым ходом ядра.

1. **Процесс убит извне вместе с родителем.** Гейтвей стартовал как дочерний от сессии агента/
   терминала; закрытие родителя (или `Stop-Process` по маске `node.exe` в чужом скрипте) уносит его.
   Самая «лошадиная» гипотеза: `klas.ps1 down` гасит node **по строке команды**, но любой другой
   массовый `Stop-Process node` — нет.
2. **Необработанное исключение в канале/сайдкаре.** `starting channels and sidecars…` — падение
   плагина могло уронить процесс без записи в JSONL-лог (вывод шёл в потерянный stdout).
3. **Нехватка памяти.** 32 ГБ RAM делятся с LLM-стеком и docker; OOM-kill node не логирует сам.
4. **Плановый выход по health-monitor.** В логе виден `[health-monitor] started (interval: 300s…)` —
   надо прочитать, есть ли у него право завершать процесс.

ровно ту улику, ради которой делается.

## Решения, принятые без владельца

- **Логи кладу в `F:\KLAS\logs\`, а не в `%TEMP%`.** Временная папка чистится Windows — улика может
  исчезнуть до того, как её прочтут. Проект уже игнорирует `logs/`, новых сущностей ноль.
- **Файл на каждый запуск вместо одного растущего.** Дороже по числу файлов, но не теряет
  предсмертный вывод при перезапуске; ротацию не пишу, пока не понадобится (Оккам).
- **Гейтвей перезапущен в ходе проверки** (он был поднят и работал). Правку нельзя было объявить
  рабочей, не прогнав её на живом процессе; простой — секунды, владельца за компом нет.
