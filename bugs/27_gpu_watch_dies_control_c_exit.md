# Bug 27 — Наблюдатель видеокарты умирает молча с кодом STATUS_CONTROL_C_EXIT

**Статус:** 🟡 частично — КЛАСС закрыт самолечением, КОРЕНЬ не установлен
**Версия/сборка:** `tools/gpu-watch.ps1` (первая версия, 2026-08-16) · Windows PowerShell 5.1 ·
задача планировщика `KLAS-gpu-watch`
**Когда/контекст:** 2026-08-16, в тот же день, когда датчик написан — пойман проходом `/fable-judge`
перед push при закрытии чата. Без этого прохода эстафета следующей сессии утверждала бы «датчик
работает», а он был мёртв уже десять минут.

## Симптом

Наблюдатель, запущенный задачей планировщика, проработал **~16 минут** и исчез. Ни строки `stop` в
журнале, ни файла `STOP`, ни ошибки на экране: задача перешла в состояние `Ready`, процесса нет.
Журнал обрывается последней контрольной строкой.

Дефект относится к худшему классу — **тихий**: для фазы 1 продукт работы это НЕПРЕРЫВНЫЕ сутки
записи, и молчаливая смерть даёт не пустой результат, а ЛОЖНЫЙ — журнал выглядит нормальным, просто
короче, и следующая сессия принимает его за полный.

## Воспроизведение (детерминированное)

Пока НЕ воспроизведён по требованию — смерть наблюдалась один раз, спустя ~16 минут работы.
Наблюдаемость обеспечена, поэтому следующий случай будет пойман:

```powershell
Get-ScheduledTaskInfo -TaskName 'KLAS-gpu-watch' | Select-Object LastRunTime,LastTaskResult
node tools/gpu-watch-replay.mjs   # печатает разрывы журнала > 10 минут
```

## Криминалистика

| Что | Значение |
|---|---|
| `LastTaskResult` | **3221225786** = `0xC000013A` = **STATUS_CONTROL_C_EXIT** |
| Запуск задачи | 2026-08-16 14:25:56 |
| Последняя строка журнала | 2026-08-16 14:41:46 (контрольная, `ev: hb`) |
| Обнаружено | 2026-08-16 14:52:47, состояние задачи `Ready` |
| Строка `stop` в журнале | ОТСУТСТВУЕТ ⇒ вышел НЕ через выключатель |
| Файл `STOP` | отсутствует |
| Журнал планировщика | `Microsoft-Windows-TaskScheduler/Operational` пуст (по умолчанию выключен) — свидетелей нет |

`0xC000013A` означает буквально одно: процесс завершён **консольным сигналом прерывания**
(CTRL_C_EVENT / CTRL_CLOSE_EVENT), а не собственной ошибкой и не убийцей извне.

## Корневая причина / Гипотезы

Корень НЕ установлен. Гипотезы по убыванию правдоподобия (`PHILOSOPHY.md` — лошади, не зебры):

1. **Консольный сигнал из соседнего процесса той же сессии.** Скрытый `powershell.exe`, поднятый
   планировщиком в сессии пользователя, получает консоль; консольный сигнал рассылается ВСЕЙ группе,
   присоединённой к консоли. В те же минуты в этой сессии агент гонял свои инструменты. Родня по
   классу уже оплачена в этом же чате: `Select-Object -First N` в конвейере УБИЛ нативный процесс на
   середине (досье окружения `AGENT_GUIDE.md`).
2. **Бесконечный цикл в `-File` скрипте по построению чувствителен к Ctrl-C** и не имеет переносимого
   способа его игнорировать. То есть даже при найденном источнике сигнала лечить надо не скрипт.
3. Сторонний софт владельца (Armoury Crate, NVIDIA app, антивирус) прибил скрытый `powershell`.
4. ⛔ Ограничение задачи по времени — **опровергнуто**: `ExecutionTimeLimit` снят, а смерть наступила
   через 16 минут.

## План фикса (сделано)

Лечится КЛАСС, а не гипотеза, — фикс верен при любой из причин выше.

- [x] **Задача перезапускает датчик сама:** к триггеру «вход в систему» добавлен повтор **каждые 5
      минут**. Умер — вернётся не позже чем через 5 минут.
- [x] **Повтор безопасен благодаря мьютексу:** живой датчик держит `Local\klas-gpu-watch`, поэтому
      каждый лишний запуск отказывается стартовать с кодом 1 и не плодит второй журнал. Мьютекс был
      добавлен раньше и по другой причине — здесь он оказался тем, что делает самолечение возможным.
- [x] **Разрыв невозможно не заметить:** `node tools/gpu-watch-replay.mjs` печатает все разрывы
      журнала > 10 минут. Критерий Ф1-1 (сутки без разрывов) проверяется машиной, а не доверием.
- [ ] **Корень.** Если разрывы продолжатся при живом повторе — ставить `Start-Transcript` или писать
      причину выхода в журнал через `[Console]::CancelKeyPress`, чтобы поймать сам сигнал.

**Проверка наблюдением — МУТАЦИЕЙ, а не доверием** [TESTED: 2026-08-16 14:54 +03:00]: датчик убит
принудительно (`Stop-Process -Id 8004 -Force`) в **14:54:16**; сразу после убийства живых экземпляров
ноль. **Вернулся САМ в 14:54:57** (`LastRunTime` задачи), pid 41368, session=1 — без человека и без
единой команды. Именно так проверяется критерий П6 эпика («сторож переживает собственную смерть»):
охранник, которому ни разу не подавали тот дефект, ради которого он существует, не доказывает ничего.

## Решения, принятые без владельца

- **Повтор раз в 5 минут, а не «служба».** Служба живёт в сессии 0 и слепа к простою владельца
  (`researches/29`) — именно поэтому датчик и стоит задачей в сессии пользователя. Значит
  устойчивость покупается повтором, а не сменой хоста.
- **Корень оставлен неустановленным, и это записано вслух.** Выдуманная причина хуже отсутствующей
  (`PHILOSOPHY.md`, правило трёх дверей); класс закрыт независимо от неё.
