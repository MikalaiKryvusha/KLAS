# `bugs/` — дефекты, трудности, поломки

Один документ на дефект: симптом, детерминированное воспроизведение, криминалистика, корневая причина /
гипотезы, история фиксов, статус. Собственный долговечный беклог багов агента — ничего не теряется, и
любой баг может быть подхвачен «с холода» будущей сессией. Один `NN_<name>.md` на баг.

**Человеку (владельцу):** можешь завести баг здесь простыми словами (что не так, как воспроизвести);
агент его структурирует. Просматривай директорию, чтобы видеть известные дефекты и их статусы.

**ИИ-агенту:** встретил дефект в ходе работы/тестирования — заведи его здесь по канону (скилл:
`/report-bug`; метод: `BUG_FIXING_FRAMEWORK.md`) — даже мелкий. Документ бага несёт наблюдаемый
критерий приёмки фикса — что будет ВИДНО работающим после фикса (`REQUIREMENTS_FRAMEWORK.md`). Пока
открыт — без тега `DONE`. Когда починен **и проверен** — `git mv NN_x.md NN_DONE_x.md` и добавь
секцию `## ✅ STATUS: DONE (дата и время)`. После 3 неудачных слепых попыток фикса — стоп и переход
к исследованию (`/bug-research`).

**Поддиректория `bugs/KAIF/`** — дефекты и запросы на улучшение о **самом фреймворке KAIF**, а не об
этом проекте. Когда сбой восходит к дыре в KAIF (правило ввело в заблуждение, не хватило гвардрейла,
сломалась машинерия) — заведи документ там по тому же канону багов, **строго на английском** (эти
документы адресованы разработчику KAIF). Перед заведением — дедупликация: сначала поищи в
`bugs/KAIF/`; развёртывания с привязкой к origin ищут ещё и в issue-трекере origin и отправляют
подтверждённые сигналы наверх, отвязанные — держат всё локально.
