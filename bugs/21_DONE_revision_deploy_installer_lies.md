# Bug 21 — РЕВИЗИЯ 2026-07-31, часть 3: деплой и установщик врали об успехе; дрейф пинов и гигиены

**Статус:** ✅ ПОЧИНЕНО (2026-07-31, коммиты `b46e137`, `28c00f6`)
**Где:** `tools/deploy.manifest.json`, `tools/deploy.mjs`, `tools/install.mjs`,
`tools/health-check.ps1`, `tools/klas.ps1`, `.gitignore`, `openclaw/openclaw.json.example`,
`docker-compose.yml`, рабочие копии двух `.bat`

## Главное — свежий клон получал НЕРАБОЧЕЕ ядро

`deploy.manifest.json` пинил движок **b9538**, тогда как бой с 2026-07-28 на **b10167**, и
канон прямо говорит: b9538 не умеет парсить тул-коллы Qwen3.6 (`bugs/05`). То есть главная
фича проекта — «clone + deploy» (идея 03) — раздавала комбинацию, в которой агентное ядро не
может звать инструменты. Дрейф жил незамеченным, потому что на машине владельца `check`
проходит по живому файлу. Комментарий манифеста «пины меняются осознанным коммитом»
существовал — коммита не было. Пин поднят; в манифест вписано правило «меняешь боевой билд —
меняй пин».

## Цепочка «все проверки успеха — фикции»

Три звена, каждое само по себе выглядит мелочью, вместе — установщик, который НЕ УМЕЕТ
сообщить о провале:

1. **`health-check.ps1` всегда выходил кодом 0** (`SilentlyContinue`, ни одного `exit`) —
   catch-ветки в `deploy.mjs`/`install.mjs` были недостижимы. Теперь счётчик проблем и exit 1.
   Попутно комментарии «kiwix маппит тот же 8080» отставали от реальности на месяц (8081 с бага 01)
   и уводили диагностику по ложному следу.
2. **`install.mjs` отмечал фазы done безусловно** и рисовал экран «KLAS установлен и работает!»
   со ссылками на мёртвый чат даже при провале деплоя. Теперь провал останавливает мастера до
   пост-настройки; состояние сохраняется — повторный запуск продолжает.
3. **`klas.ps1` глотал провал `docker compose`** (`catch {}` + `Out-Null`) и слал пуш
   «KLAS запущен и работает» при лежащем Docker Desktop. Теперь трей говорит «поднят ЧАСТИЧНО».

Плюс `install.mjs` решал «ставить docker-stack» по НАЛИЧИЮ CLI, игнорируя честно вычисленный
`env.dockerRunning` (типичное после ребута «установлен, но не запущен» валило compose молча).

## Докачка: полный `.part` = вечный клин HTTP 416

Процесс, убитый между концом загрузки и `renameSync` (у 7-ГБ модели окно подсчёта sha ~30 с),
оставлял `.part` полного размера. Следующий запуск слал `Range: bytes=<всё>-`, получал 416 и
падал; `.part` никто не чистил — и так по кругу. Теперь 416 при непустом `.part` = «файл полон,
финализируй» (sha/размер всё равно судят дальше).

## Мёртвый код, найденный по несуществующему импорту

`deploy.mjs --with-kaif` звал `writeFileSync`, которого НЕТ в импортах: ветка падала
ReferenceError'ом с рождения — значит, её ни разу не запускали. Импорт добавлен. Урок для
ревизий: **несуществующий импорт = доказательство, что ветка никогда не исполнялась.**

## Гигиена, закрытая тем же заходом

- `.gitignore`: не было `/.deploy-cache/` (150+ МБ zip'ов движка ждали `git add -A`);
  правило `/kiwixdb/` не совпадало регистром с фактической `KiwixDB` (держалось только на
  `core.ignorecase`; в WSL .zim-гигабайты стали бы untracked); маски ключей ловили только
  `*.ts.net.*` — добавлены `*.key`/`*.pem`/`id_rsa*` (инцидент 2026-07-18 был именно «ключ
  с другим именем»).
- `openclaw/openclaw.json.example`: три поля `name` — моджибейк CP1251 (класс `bugs/08`,
  но в ШАБЛОНЕ, который деплой копирует каждой новой установке). Перенабраны.
- Рабочие копии `start-llama-swap.bat` (автозапуск стека!) и `tailscale_funnel_443.bat` лежали
  с LF вопреки `attr eol=crlf` — кто-то перезаписал их инструментом, пишущим LF; парсер cmd
  на LF ломается непредсказуемо (баг 01). Пересозданы из индекса. ⚠️ Атрибуты НЕ защищают уже
  существующие рабочие копии — сверка `git ls-files --eol | grep 'crlf.*w/lf'` предложена в
  сторожа гигиены (ideas/16).
- `docker-compose.yml`: маунт `docker.sock` в homepage при ВЫКЛЮЧЕННОМ docker-провайдере —
  root-эквивалентный доступ к хосту у контейнера за funnel, без какой-либо пользы. Снят
  (применится при следующем recreate).
- Транскрипт Гороховой (`.txt` в корне) был затрекан в публичный git вопреки собственному
  правилу «исходники голоса — в git НИКОГДА». Снят с трекинга, перенесён в `voice/sources/`.
  ⚠️ В ИСТОРИИ git файл остаётся — чистка истории меняет хеши и делается только решением
  владельца (вопрос — в `researches/19`).
